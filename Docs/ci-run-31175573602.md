## Cause

WebKit 6 has no unsandboxed mode: it launches its network and web processes
through `bwrap`, which starts by creating an unprivileged user namespace.
Docker's default seccomp profile refuses `clone(CLONE_NEWUSER)`, and the job's
`container: debian:forky` is subject to it:

```console
$ docker run --rm debian:forky unshare -U true
unshare: unshare failed: Operation not permitted
$ docker run --rm --security-opt seccomp=unconfined debian:forky unshare -U true
$ echo $?
0
```

WebKit does not report the refusal as a failed call. It calls `g_error`, which
aborts the process and takes the test host with it — nothing managed can catch
it.

Which tests reach it, established by running each in isolation:

| Filter | Result |
|---|---|
| `FullyQualifiedName~OptionalLibraryTests` | Passed 2/2 — constructing a `WebKit.WebView` never reaches the sandbox |
| `FullyQualifiedName~SampleSectionTests` | **aborted** after 18 |
| `FullyQualifiedName~SectionBrowsingTests` | **aborted** |

All of them go through `Samples.WebviewSection`, which calls `LoadHtml` and
`LoadUri` in its constructor — *loading a page* is what spawns the sandboxed
processes. `ChildWindowTests` constructs every section too, so it is the third
entry point.

This is the first CI run since `WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS` was
deliberately dropped from the workflow, which is why it had not been seen
before; [Docs/testing.md](testing.md) still passed that flag for local container
runs, so it did not show there either.

## Fix

The workflow's own comment prescribed the answer: *"If bwrap still cannot start
in a future runner image, skip the WebKit-backed sections rather than restoring
the flag."*

- **New** [Source/Tests/GtkSharp.Tests/TestEnvironment.cs](../Source/Tests/GtkSharp.Tests/TestEnvironment.cs)
  — `GTKSHARP_TESTS_SKIP_WEBKIT`, and the distinction that matters: WebKit being
  *absent* (Windows, where the section degrades to a label and constructs fine)
  is not WebKit being *unable to sandbox itself* (here, where it aborts).
- `SampleSectionTests`, `ChildWindowTests` and `OptionalLibraryTests` skip the
  WebKit cases; `SectionBrowsingTests` skips the WebView row, and the two facts
  that reach a section positionally through the tree step over it.
- The workflow sets `GTKSHARP_TESTS_SKIP_WEBKIT: 1` on the test step.

### Why the switch is explicit rather than inferred

An automatic probe was written first and **withdrawn as unsound**. Running the
operation bwrap begins with — `bwrap --unshare-user --ro-bind / / /bin/true` —
succeeds in a container where WebKit still aborts. A shim over `/usr/bin/bwrap`
that logs argv shows why: WebKit makes four calls, of which the first is a
capability check shaped like the probe and passes, and the failing one is

```text
bwrap --args 217 -- /usr/bin/xdg-dbus-proxy --args=213
```

reporting `Creating new namespace failed: Operation not permitted` — bubblewrap's
message for a namespace other than the user one, not the
`No permissions to create a new namespace…` that a blocked `CLONE_NEWUSER` gives.
A probe that can answer "usable" and then abort is worse than none: a wrong
"skip" costs one section, a wrong "run" costs the whole suite.

### Why the container is not simply loosened

Measured on one image, running only `SampleSectionTests`:

| container | result |
|---|---|
| *(default — what CI has)* | aborts, 18 of 32 |
| `--security-opt seccomp=unconfined` | aborts, 18 of 32 |
| `--privileged` | 32 of 32 |

`seccomp=unconfined` restores `unshare -U true` and standalone bwrap — Docker's
default profile is what blocks `clone(CLONE_NEWUSER)` — and is still not enough
for WebKit. Only `--privileged` is, and that is a far wider grant than a job
holding a `packages:write` token should have.
